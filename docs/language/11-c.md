# 11. C

Wip calls C directly: no bindings layer, no marshalling, and no generated
glue except where only C can reach something — a macro, or a `static
inline` function.

## `extern "C"`

An `extern "C"` block declares what C has. Inside it, functions, variables
and opaque types are written as Wip would write them, in C's types:

```wip,run
@link("m")
extern "C" {
    fn sqrt(x: f64): f64
    fn strlen(s: cstring): u64
}

fn main() = {
    assert(sqrt(9.0) == 3.0)
    var text = String::of("four")
    assert(strlen(text.toCstring()) == 4)
}
```

- **`@link("m")`** names a library to link, as `-lm` does, and
  `@link("X11", "GL", "asound")` several, linked in that order.
- **`@header("<math.h>")`** names the header the declarations come from.
  On a block, it is where the block's types are. On one function or
  variable, it says the header *defines* it — a macro or a `static inline`,
  which has no symbol — so each use goes through C the compiler writes,
  which includes the header.
- **`@symbol("sqlite3_open")`** gives a declaration the C name it really
  has, where Wip calls it something else.
- **`@include("src")`** adds a directory of the module to the include path
  of the C compiled with it, and **`@framework("Cocoa")`** names what an
  Apple target links besides its libraries.

A block may declare C's types beside C's functions, which is where a
binding puts them:

```wip
@header("shapes.h")
extern "C" {
    pub struct Point {
        x: f64
        y: f64
    }

    fn quadrant(p: Point): i64

    @header("shapes.h")
    fn area(p: Point): f64
}
```

Inside a block, `struct` and `union` are C's layout — the block already
said `extern` — and they take the block's `@header`. A type that belongs
to no block is written `extern struct Point { … }` with a header of its
own. `quadrant` is called directly; `area` is a `static inline` the header
defines, so it names the header itself.

A struct crosses by value the way C passes it on the target: in registers
where it is small enough, through a copy or on the stack where it is not.
A union crosses the same way, by the rules C has for one.

A C struct is built as C builds one: a field it is not given is zero — a
number, a null `ptr<T>` or `cstring`, and a nested struct or array zero
throughout — as C's designated initializer leaves it, which is how a C
library is told "the default". A C function pointer that may be null is
an `Option` of a function type, laid out as the pointer with `.None` as
null; C calls one given as `.Some(f)`. It is a field, a parameter or a
result, and crosses as the one pointer C's is:

```wip,run
extern "C" {
    pub struct AppDesc {
        frame_cb: Option<() => void>
        cleanup_cb: Option<() => void>
        width: c_int
        height: c_int
        window_title: cstring
        sample_count: c_int
    }
}

fn frame() = {}

fn main() = {
    val desc = AppDesc(width: 448, height: 576, frame_cb: .Some(frame))
    assert(desc.sample_count == 0 && desc.cleanup_cb.isNone())
    assert(desc.frame_cb.isSome())
}
```

## More arguments than declared

A C function declared with `...` takes more than it names, and a call
passes them by position:

```wip,run
extern "C" {
    fn printf(format: cstring, ...): c_int
}

fn main() = {
    val pears: f32 = 2.5
    assert(printf("%d apples, %.1f pears\n", 3 as c_int, pears) == 20)
}
```

What follows the declared parameters is a scalar C knows — an integer, a
float, `bool`, `cstring` or `ptr<T>` — and the compiler promotes it as C
does: an `f32` becomes a `double`, and an integer narrower than `int`
becomes an `int`. Nothing is widened in the program itself, so `3 as c_int`
says what `%d` reads.

## C's variables

`var` and `val` in a block are variables C owns. `val` is read, `var` is
read and written, and each use is a load or a store of C's own symbol, so C
sees every write:

```wip
extern "C" {
    var counter: c_int
    val greeting: cstring

    // A macro, not a symbol: C reads it for Wip.
    @header("<errno.h>")
    var errno: c_int
}
```

A variable with its own `@header` may be a macro, as `errno` is, and is
read and written through C the compiler writes.

## C's types

| Wip | C |
|---|---|
| `c_char`, `c_uchar`, `c_short`, `c_ushort`, `c_int`, `c_uint`, `c_long`, `c_ulong`, `c_longlong` | the matching C types, whatever they are on the target |
| `size_t`, `ssize_t`, `intptr_t`, `uintptr_t` | the same |
| `cstring` | `const char *`, zero-terminated, or null |
| `ptr<T>` | `T *` |
| `f32`, `f64` | `float`, `double` |
| `void` | `void` |

A C type whose contents a program is not told — `typedef struct sqlite3
sqlite3;` — is declared `type sqlite3` in the block, and is only ever
pointed at: a `ptr<sqlite3>` is a value, and a `sqlite3` is not, since how
large one is is C's business. It may be a type argument, of a generic
that only points at it; an instance that would hold a value of it, or ask
its size, is refused where it does:

```wip,run
import std::collections::{Map}

extern "C" {
    type Handle
}

/// What a program has made, by name.
struct Made<T> {
    byName: Map<String, ptr<T>>
}

fn main() = {
    var made: Made<Handle> = Made(byName: Map())
    made.byName.put(String::of("none"), null)
    assert(made.byName.at(String::of("none")).isNull)
}
```

A `bool` is C's `bool`, and one C hands over is read as C converts a byte
to one: zero is false and anything else is true. C may leave any byte
where it declares a `bool` — a struct filled from a file, a field it
forgot, a flag that is a `uint8_t` on its side — and Wip's own `!` and
`==` count on a `bool` being 0 or 1. So what a C function answers, a C
variable, a field of an `extern struct` or `extern union` wherever it
lies, and a parameter of a function C calls are each compared with zero
where Wip reads them. What a `ptr<bool>` points at is read as it is: a
pointer reaches what the program says it does.

```wip,run
import flags::{flag}

fn main() = {
    val b = flag()
    assert(b && !(!b) && b == true)
}

// file: flags/flags.wip
extern "C" {
    pub fn flag(): bool
}

// file: flags/flags.c
#include <stdint.h>

uint8_t flag(void) {
    return 2;
}
```

Two pointers compare with `==` and `!=`, by where they point, and `null`
takes the type of the pointer on the other side: `handle == null`.
A pointer has no order. It converts with `as` to the
integer that is its address, and back — `handle as usize`, `address as
ptr<Node>` — where the integer is as wide as a pointer: `usize`, `isize`,
`u64` or `i64`.

`p[i]` is the element `i` counted from where `p` points, read or written,
and `p.field` is C's `p->field`. `&p[a..b]` and `&var p[a..b]` are the
slice of the elements `a` to `b`: memory C hands over, as many elements as
the range says. Only the program knows how many there are, so a range of
a pointer has an end, and nothing is checked but that it is a range — its
start no further than its end, neither negative. Each is written however
the pointer is held, since what a `val` keeps is the pointer, not what it
points at, and a slice of C's memory is as good as C keeps it. A
`ptr<void>`, and a pointer to a C type whose contents Wip does not know,
is cast first: an element needs a size.

```wip,run
import buffers::{numbers}

fn main() = {
    val p = numbers()
    assert(p[3] == 4)
    val given: [i32; 2] = [10, 20]
    p[0..2].copyFrom(&given)
    val first = &p[0..3]
    assert(first.len() == 3 && first[1] == 20 && first[2] == 3)
}

// file: buffers/buffers.wip
extern "C" {
    pub fn numbers(): ptr<i32>
}

// file: buffers/buffers.c
#include <stdint.h>

static int32_t kept[4] = {1, 2, 3, 4};

int32_t *numbers(void) {
    return kept;
}
```

`cstring` is not `str`: it is zero-terminated and knows no length.
`text.toCstring()` makes one from a `String` (it appends the zero byte), and
`cstring::toStr()` reads one back, counting its bytes. What it reads
borrows where the C string is: a function given `main`'s `args` may answer
the `str`s it read from them, which borrow `args`.

A C string made from a `String` points into the `String`'s bytes, and is
checked as a `str` is: it may be used while the `String` is there and
unchanged, and is refused after — kept past a `String` that was a
temporary, used after the `String` changed (another `toCstring()` among
the changes, since it may move the bytes), or returned borrowing a
`String` that ends. A value that holds one borrows what it does. A C
string from C, or a literal, borrows nothing of the program's, and may be
kept anywhere; what C does with a pointer it is given is C's contract,
which the checker does not see.

```wip,error=E0436
extern "C" {
    fn strlen(s: cstring): size_t
}

fn main() = {
    var text = String::of("hello")
    val c = text.toCstring()
    text.push(" again")
    assert(strlen(c) == 5)
}
```

A `cstring` may be null, as C's may: C answers one where there is
nothing, `null` is passed where C takes none, and a C struct's string left
out of its literal is one. `isNull` asks, and so does comparing with
`null`, which has no text to compare; two `cstring`s compare by their
text. A null one read as text — `toStr()`, comparing two, hashing or
formatting one — panics, rather than read what is at address zero:

```wip,run
extern "C" {
    struct Window {
        title: cstring
        width: c_int
    }
}

fn main() = {
    val plain = Window(width: 640)
    assert(plain.title.isNull && plain.title == null)
    val named = Window(title: "wip", width: 640)
    assert(named.title != null && named.title.toStr() == "wip")
}
```

A `str` or a `&[T]` passed to a C function is passed as two arguments, the
pointer and the length, since that is what C functions take.

A C function that writes what it makes where a pointer points — a
handle, a count, the array it fills — takes a `ptr<T>`, and a call lends
it a place: `&var x` for C to write, `&x` for it to read. An array or a
slice of `T`s is lent as the address of its first element, a `ptr<void>`
takes the address of anything, and `null` is passed where C allows none.
Each is lent for the call, as a reference argument is: a `val` is not
lent `&var`, one place is not lent twice to a call, and C keeps nothing
past it. Only C's functions are lent to this way; a Wip function that
writes through a reference says `&var T`.

```wip,run
import listing::{list}

fn main() = {
    var count: u32 = 0
    list(&var count, null)
    var items: [u32; 8] = [0; 8]
    list(&var count, &var items)
    assert(count == 3 && items[2] == 12)
}

// file: listing/listing.wip
extern "C" {
    pub fn list(count: ptr<u32>, items: ptr<u32>)
}

// file: listing/listing.c
#include <stdint.h>

void list(uint32_t *count, uint32_t *items) {
    if (!items) {
        *count = 3;
        return;
    }
    for (uint32_t i = 0; i < *count; i++) {
        items[i] = 10 + i;
    }
}
```

A C struct's pointer field takes `&x` in its literal, as a C function's
pointer parameter does — one value, an array, a slice, anything for a
`ptr<void>`, and `&var x` for one C writes through — and the struct then
borrows what it points at, as a value holding a C string made from a
`String` borrows it: one used after that changed is refused (E0436), and
one returned from the function that points at its local (E0437). This is
how a library that describes what it makes with structs pointing at
structs is told it:

```wip
extern "C" {
    struct Range {
        start: ptr<u8>
        count: c_int
    }

    struct Request {
        range: ptr<Range>
        flags: c_int
    }

    fn sum_bytes(request: &Request): c_int
}

fn total(bytes: &[u8]): i64 = {
    val range = Range(start: &bytes, count: bytes.len() as c_int)
    return sum_bytes(Request(range: &range, flags: 0)) as i64
}
```

A function may answer such a struct, and it borrows what the function's
signature lends, as a view holding a `&` does ([page 7](07-references.md)):
a `ptr<T>` field refers to a `T`, and a `ptr<void>` to anything, so a range
made over the bytes a function is given borrows them where it is used. One
a C function answers borrows nothing, and neither does one that comes
through a type parameter, made where its value was:

```wip,run
extern "C" {
    struct Range {
        start: ptr<u8>
        count: c_int
    }
}

/// The range over all of `bytes`, which it borrows.
fn rangeOf(bytes: &[u8]): Range = Range(
    start: &bytes,
    count: bytes.len() as c_int,
)

fn main() = {
    val bytes: Vec<u8> = Vec::of(own [1, 2, 3])
    val range = rangeOf(&bytes.items())
    assert(range.count == 3)
}
```

A pointer made as a value apart from a C struct is
`c::pointerTo(&values)`: the address of a slice's first element, for C to
read while the slice is lent, which nothing checks.

An array by reference is passed as the address of its first element, which
is what C's `T x[N]` parameter is: `&[T; N]` for C to read and `&var [T; N]`
for it to write, where C can hold the elements. An array by value does not
cross; C cannot take one. C's pointer-sized integers are built in by C's
names — `size_t`, `ssize_t`, `uintptr_t`, `intptr_t` — and `usize` and
`isize` stay Wip's own:

```wip,run
import digits::{fill}

fn main() = {
    var out: [u8; 4] = [0; 4]
    fill(&var out)
    assert(out[0] == 1 && out[3] == 4)
}

// file: digits/digits.wip
extern "C" {
    fn digits_fill(out: &var [u8; 4])
}

pub fn fill(out: &var [u8; 4]) = digits_fill(&var out)

// file: digits/digits.c
#include <stdint.h>

void digits_fill(uint8_t out[4]) {
    for (int i = 0; i < 4; i++) {
        out[i] = (uint8_t)(i + 1);
    }
}
```

## C files in a module

Every `.c` file beside a module's `.wip` files is compiled and linked with
the program, and the module's directory is searched for what any of the
program's C includes with quotes, `#include "counter.h"`, so its C finds its
own headers; C++ files are too, as below. It is not searched for
`#include <…>`, which is the system's: a module's `math.h` is not
`<math.h>`, nor, on a disk that ignores case, its `metal.h`
`<Metal/Metal.h>`. On an Apple target, `.m` files are compiled as well:

```wip,run
import counter::{next}

fn main() = {
    assert(next() == 1)
    assert(next() == 2)
}

// file: counter/counter.wip
extern "C" {
    fn counter_next(): i64
}

pub fn next(): i64 = counter_next()

// file: counter/counter.c
#include <stdint.h>

static int64_t counted = 0;

int64_t counter_next(void) {
    return ++counted;
}
```

A library vendored in the module — its own tree, as it was released —
is named rather than found, and what configures it is said once for all
of its files:

```wip,ignore
@source("src/rcore.c", "src/rshapes.c", "src/rtextures.c")
@define("PLATFORM_DESKTOP", "GRAPHICS_API_OPENGL_33")
@include("src")
@header("raylib.h")
extern "C" {
    fn InitWindow(width: c_int, height: c_int, title: cstring)
}
```

`@source` names C files of the module, each compiled as its own
translation unit; a path that leaves the module is refused. `@prefix` is
the header every C file of that module is compiled with — `cc -include` —
which is where a setting that needs a comment, a condition or more than a
line goes.

A single-header library — sokol, the stb libraries, miniaudio — is built
from its header: `@source` names the header, which is then compiled as the
implementation it holds, and `@define` says which part. A file is C or
Objective-C by its extension, and `language = "objective-c"` says so of
one that is not a `.m`, as a Mac's window layer needs:

```wip,ignore
@target(vendor = "apple")
@source("sokol.h", language = "objective-c")
@define("SOKOL_IMPL", "SOKOL_METAL", "SOKOL_NO_ENTRY")
extern "C" {}

@target(os = "linux")
@source("sokol.h")
@define("SOKOL_IMPL", "SOKOL_GLCORE", "SOKOL_NO_ENTRY")
extern "C" {}
```

C++ is built the same way. A `.cpp`, `.cc` or `.cxx` file beside a
module's `.wip` files is compiled as C++, a `.mm` file as Objective-C++ on
an Apple target, and `language = "c++"` or `"objective-c++"` says so of a
header that holds a library's implementation. C++ is compiled to C++17
unless `standard` says another, `"c++11"` to `"c++23"`, and the C++
library is linked wherever C++ was compiled. Wip calls C++ through C: what
it declares are `extern "C"` functions, and a class, a template or an
exception does not cross — an exception that reaches Wip's frames ends the
program, as one nothing catches ends a C++ one:

```wip,run
import totals

fn main() = assert(totals::totals_sum(4) == 10)

// file: totals/totals.wip
extern "C" {
    pub fn totals_sum(n: i64): i64
}

// file: totals/totals.cpp
#include <numeric>
#include <vector>

extern "C" long totals_sum(long n) {
    std::vector<long> values(n);
    std::iota(values.begin(), values.end(), 1);
    return std::accumulate(values.begin(), values.end(), 0L);
}
```

Assembly is built the same way too: `@source` names `.s` and `.S` files,
which the C compiler assembles, a `.S` through the C preprocessor with the
module's `@define`s, and Wip calls what they define through `extern "C"`,
as a C function. A file is written for one processor, so each goes in an
`extern "C" {}` block of its own `@target`. What one instruction does is a
method of the library, as the bit counts are; a routine of many, for one
processor, is a file:

```wip,run
import adds

fn main() = assert(adds::adds_add(40, 2) == 42)

// file: adds/adds.wip
@target(arch = "arm64")
@source("add_arm64.S")
extern "C" {}

@target(arch = "x86_64")
@source("add_x86_64.S")
extern "C" {}

extern "C" {
    pub fn adds_add(a: i64, b: i64): i64
}

// file: adds/add_arm64.S
#if defined(__APPLE__)
#define NAME(n) _##n
#else
#define NAME(n) n
#endif
    .text
    .globl NAME(adds_add)
    .p2align 2
NAME(adds_add):
    add x0, x0, x1
    ret

// file: adds/add_x86_64.S
#if defined(__APPLE__)
#define NAME(n) _##n
#else
#define NAME(n) n
#endif
    .text
    .globl NAME(adds_add)
NAME(adds_add):
    leaq (%rdi,%rsi), %rax
    ret
```

Wip writes no assembly inside a function: a file says what a routine for
one processor does, at the cost of a call.

A setting that is one name, or a name and a value, is `@define`, which is
what `-D` passes, for every C file of the module:

```wip,run
import tally

fn main() = {
    assert(tally::next() == 42)
    assert(tally::next() == 44)
}

// file: tally/tally.wip
@define("START=40", "STEP=2", "LOUD")
extern "C" {
    fn tally_next(): i64
}

// A setting for one target is a block of its own.
@target(vendor = "apple")
@define("ON_APPLE")
extern "C" {}

pub fn next(): i64 = tally_next()

// file: tally/tally.c
#include <stdint.h>

static int64_t counted = START;

int64_t tally_next(void) {
    counted += STEP;
    return counted;
}
```

The names come before the prefix header, so a header may build on them.

Each C file is compiled once and kept in a cache, keyed by the compiler, the
flags, the file and the headers it reads, so a build that changes nothing in
C compiles none of it again. This is how a game can build raylib from its
source, vendored beside it, with every build of its own.

## C calling Wip

`@export("C")` gives a function a plain C symbol, its own name, so C can
call it:

```wip
@export("C")
pub fn wipAdd(a: i64, b: i64): i64 = a + b
```

A C struct or union may cross by value here too. A call from C has no
wrapper to fall back on, so taking such an export as a Wip function value
is refused: C passes the struct in registers, and a Wip function value
takes its address. A function passed to C as a callback takes and answers
scalars and pointers only, and no function pointer that may be null: C
would pass either in registers, and a Wip function value takes its
address.

A C library that calls back gives the callback a `void *` the program
chose. `std::c` lends a value to C as that pointer, for as long as a call
runs, and has it back in the callback as the `&var` it is:

```wip
import std::c

struct Game {
    ticks: i64 = 0
}

// What C calls, with the `void *` it holds.
fn frame(data: ptr<void>) = c::lentBack(data, (game: &var Game) =>
    game.ticks += 1)

fn main() = {
    var game = Game()
    c::lending(&var game, (data) => frame(data))
    assert(game.ticks == 1)
}
```

Nothing else touches the value while it is lent, and the type the
callback names is the one thing the checker cannot see.

A library that keeps what it is given past the call — a file watcher's
`info`, a timer's context — and calls back later, maybe on a thread of
its own, is given a `c::Pinned`: a value on the heap whose address C may
hold for as long as the `Pinned` lives. The program reads it with
`value()`, and the callback has it back with `c::pinnedAt`; both read it
through a `&`, so what changes is an `Atomic` or a `Mutex` inside it.
The program tells C to let go before the `Pinned` ends,
as in C:

```wip,run
import std::c
import std::sync::{Atomic}

struct Ticks {
    count: Atomic<i64>
}

// What a C library would call, later, with the address it kept.
fn tick(data: ptr<void>) = c::pinnedAt<Ticks, void>(data, (ticks) => {
    ticks.count.add(1)
})

fn main() = {
    val ticks = c::Pinned::of(Ticks(Atomic::of(0)))
    val kept = ticks.address()
    tick(kept)
    tick(kept)
    assert(ticks.value().count.load() == 2)
}
```

A C function told how many bytes it is given is told with `c::sizeOf<T>()`,
what C's `sizeof` answers for `T` — padding and all — and `c::alignOf<T>()`
is `_Alignof`:

```wip,run
import std::c

extern "C" {
    pub struct Vertex {
        x: f32
        y: f32
        attr: u32
    }
}

fn main() = {
    val count: size_t = 6
    assert(c::sizeOf<Vertex>() == 12 && c::alignOf<Vertex>() == 4)
    assert(count * c::sizeOf<Vertex>() == 72)
}
```

`c::offsetOf<T>("field")` is C's `offsetof`: where the field the literal
names lies in `T`, in bytes, a constant. It is what a GPU is told of a
vertex's attributes, and a top-level `assert` fails the build when the
layout and what reads it part. The name is checked as a field access is,
and an `@opaque` struct's offsets are C's, so it has none:

```wip,run
import std::c

extern "C" {
    pub struct Vertex {
        position: [f32; 3]
        uv: [f32; 2]
        color: u32
    }
}

assert(c::offsetOf<Vertex>("color") == 20, "where the shader reads the colour")

fn main() = {
    assert(c::offsetOf<Vertex>("position") == 0)
    assert(c::offsetOf<Vertex>("uv") == 12)
}
```

`c::bytesOf(&value)` is a value's bytes, as C sees them at its address —
`c::sizeOf<T>()` of them, borrowing the value — for what C or a GPU is
given as bytes: a draw's constants copied into a buffer, a file's header.
It takes numbers and what holds only numbers. A struct with a gap between
its fields or after the last is refused, since nothing writes those
bytes, and so is an enum whose variants hold values, and what holds an
address, which means nothing outside the program (E0459); a struct says
its padding with a field where it is, or `@packed`. Where a generic
function asks for a `T`'s bytes, the `T` is checked where the function is
made for it:

```wip,run
import std::c

struct Constants {
    scale: f32
    offset: f32
}

fn main() = {
    val constants = Constants(scale: 2.0, offset: 0.5)
    var buffer: [u8; 16] = [0; 16]
    buffer[0..8].copyFrom(&c::bytesOf(&constants))
    assert(buffer[3] == 0x40)
}
```

A C struct declared `__attribute__((packed))` is `@packed` in Wip, and one
or a field declared `alignas(n)` or `__attribute__((aligned(n)))` is
`@align(n)` ([page 1](01-types.md)), which is what `wip bindgen` writes. A
packing that is not 1, `#pragma pack(2)`, Wip does not say: bindgen writes
such a struct `@opaque`, its layout left to C.

`wip build --emit static` (or `dynamic`) writes a library rather than a
program, and `--header board.h` writes the C declarations for what it
exports. [Page 12](12-tools.md) has both.

## One target at a time

A library is spelled differently on different systems, and some of it does
not exist everywhere. `@target` says which target a declaration is for, and
a file may say so in its name ([page 2](02-modules.md)):

```wip,run
// The maths are part of libSystem on a Mac and a library of their own
// elsewhere, so the prelude links it only where that is so. A block that
// declares nothing but says `@link` is how a library is named.
@target(os = "linux")
@link("m")
extern "C" {}

@target(vendor = "apple")
fn platform(): str = "Apple's"

@target(os = "linux")
fn platform(): str = "a penguin's"

@target(os = "windows")
fn platform(): str = "a window's"

fn main() = {
    assert(platform().len() > 0)
    assert(
        TARGET_OS == "macos" || TARGET_OS == "linux" || TARGET_OS == "windows",
    )
}
```

An Objective-C file — `.m` — is Apple's by its extension, and a `.c` file
may say which target it is for in its name: `rglfw.macos.c`.

## What is not done for you

- **Nothing is converted** but a `bool`, as above. A `c_int` is not an
  `i64` until `as` says so; a constant is as the literal it stands for
  ([page 1](01-types.md)), so a C enum's enumerators, which bindgen writes
  as `c_int` constants, are given where C takes a `uint32_t` of flags.
- **Nothing is checked at the boundary.** C's promises are C's: a pointer
  that must not be null, a length that must be right, memory that must
  outlive the call.
- **Ownership stops at the edge.** Memory C gives is freed by C, usually in
  a `Destroy` written for a struct that holds the handle
  ([page 6](06-ownership.md)).
- **`wip bindgen`** reads a C header and writes the `extern "C"` block for
  it, with clang — the compiler `$CC` names, or the clang `$WIP_CLANG`
  names, as `wip` builds with, or `clang`: `wip bindgen raylib.h -o
  raylib.wip`. It is a Wip
  program that `wip` carries and builds the first time it is asked for. A
  `#define` that is not a literal — raylib's `(Color){ 200, 200, 200, 255
  }`, termbox's `(0xffff - 1)`, `PI / 180.0f` — is written as clang works
  it out: a struct constant, a number, a float. A C function pointer is
  written as the Wip function type a callback takes, `(a0: ptr<void>, a1:
  ptr<void>) => c_int`. A header configured by macros is read with them,
  `-D TB_OPT_ATTR_W=32`, and the block says them in an `@define`, so the C
  is compiled as it was read; `-I` names a directory the header's own
  includes are found in. It writes what the header itself declares, not
  what it includes: Vulkan's is `vulkan_core.h`, which `vulkan.h`
  includes. A pointer parameter is a `ptr<T>`, which a call lends a
  place to, except a `const` pointer to a struct the header defines, one
  struct C reads, which is a `&T`. One right after a parameter named
  `count` or `…Count` is an array, which may be empty and null, and is a
  `ptr<T>`; so is one the header marks `_Nullable`, and one `--pointer
  pAllocator` names, for what the header does not say. `--type Vector3=std::math::Vec3` declares the
  header's `Vector3` as the library's `Vec3`, which the module imports, so
  a value crosses as it is; it is refused where the two are not laid out
  alike — their size, their alignment, or a field's offset or type — as
  clang and `wip` each say.
